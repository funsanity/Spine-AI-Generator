# 去背功能

## 问题

用户上传的图往往是**白底图**（PNG 但 `channels=3 hasAlpha=false`，完全没有 alpha 通道）。这导致两处链路失效：

1. **切图切的是矩形**：`sharp.extract()` 按 bbox 切一个矩形区域，背景不透明时每个部件都是实心方块，相邻部件的白底被一起切进来，拼回场景就是一堆互相遮挡的白方块。

2. **补图判 alpha**：`buildMaskFromAlpha` 把 `alpha < 8` 的像素标成"需要补"。背景不透明就没有一处 alpha=0，所有部件都报「没有需要补的透明区」，补图功能一次都不生效。

实测一张 1728×2304 白底图生成 14 个部件，全部 0.00% 透明像素，补图日志 `0 成功，14 无需补`。

## 解决方案

在**分析之前**加一步去背：从四边泛洪，把与边缘连通的背景色清成透明。

### 为什么用泛洪而不是色键

角色内部的白（眼白、牙齿、高光、白衣服）和背景同色。全图色键会连人一起镂空。

实测同一张图：边缘连通的背景占 66.6%，全图纯白占 68.8%。那 2.2% 的差值就是必须留下的内部白。

### 实现细节

`server/api/background.js`：

1. **`detectBackground`**：四角投票取背景色。四角各不相同时返回 `null`（宁可不做也不瞎做）。
2. **`removeBackgroundPixels`**：四边全部作为种子（不是只从四角出发），用显式栈泛洪。输入可能是 3 通道，输出统一 RGBA。
3. **`recoverEdgeAlpha`**：泛洪只清"和背景几乎一样"的像素，抗锯齿留下的过渡像素比背景暗一点点、够不上阈值，被当成不透明留了下来——症状是一圈**白边**。这一步把混合反解回来：`观察值 = a·本色 + (1-a)·背景色`，解出 `a` 后把本色也还原出来，半透明像素里才不会带白。
4. **`removeBackground`**：已带 alpha 的图直接跳过。3 通道图走上面三步，结果覆盖上传的临时文件。

### 接入点

`server/index.js:324~346`，在 `const imageSize = await getImageSize(imagePath)` 之前插入：

```javascript
if (background) {
  broadcastLog('正在去除背景...', 'progress');
  const bg = await removeBackground(imagePath);
  if (bg.skipped && bg.reason === 'already-transparent') {
    broadcastLog('图片已带透明通道，跳过去背', 'info');
  } else if (bg.skipped) {
    broadcastLog('四角颜色不一致，无法判定背景色，跳过去背', 'warning');
  } else {
    await writeFile(imagePath, bg.buffer);
    broadcastLog(`✓ 去背完成：清除背景 ${(bg.ratio * 100).toFixed(1)}%，边缘还原 ${bg.feathered} px`, 'success');
  }
}
```

去背结果直接覆盖上传文件，下游分析、切图读的都是同一份，格式和路径都不变。

- 容差默认 18，可通过 `options.tolerance` 调整
- 边缘还原的 `MIN_DROP` 默认 6，防止把背景残渣拉成半透明噪点

# 补图接口的 size 参数（真实中转站踩坑记录）

## 症状

第一次真实跑补图：14 个部件 **3 成功 9 失败**，失败全部是 `HTTP 400`，响应体只回一句：

```json
{"error":{"message":"Bad request","type":"invalid_request_error","param":null,"code":"RJ_BAD_REQUEST"}}
```

失败请求 **0.3~6 秒**就返回，成功请求要 **20~40 秒**。形态上非常像限流——但**重试 3 次全败**，是确定性失败，不是瞬时故障。

## 排查过程与弯路

先怀疑图片尺寸。逐部件扫出来的分界看着毫无道理：

| 送模型尺寸 | 结果 |
|---|---|
| 1024x688 | ✓ |
| 976x736 | ✓ |
| 864x800 | ✓ |
| 832x800 | ✓ |
| 900x900 | ✗ |
| 816x816 | ✓ |
| 816x815 | ✗ |
| 800x800 | ✗ |
| 768x768 | ✗ |
| 256x576 | ✗ |

试过"总像素阈值"（900x900 有 81 万像素却挂）、"短边阈值"（816x815 vs 816x816 只差 1 像素却是两种结果）——都对不上。因为**真正的判据根本不是图片尺寸**。

真正的判据是**我们传给 `size` 字段的那个字符串**。

## 根因

`/v1/images/edits` 只认白名单里的 `size` 值。我们按部件尺寸算出来的 `768x640`、`256x576` 这类自定义值一律 400。

之前那批"部分成功"纯属巧合：只有长边正好缩到 1024、算出来的 `size` 恰好落在合法区间的那几个部件能过。所以边界看起来毫无规律。

对照实验（同一张图、同样的蒙版，只改 `size` 字段）：

| size 参数 | 结果 |
|---|---|
| `256x576`（我们算的） | ✗ 400 |
| `1024x1024` | ✓ |
| **`auto`** | ✓ |

`auto` 对所有尺寸都通过，包括 144x192 这种小图：

```
OK   送256x576 size=auto → 返回836x1880 png  17655ms
OK   送144x192 size=auto → 返回1085x1450 png  16332ms
```

三个 gpt-image 模型（gpt-image-2 / 2.5-sunburst / 2.5-flare）都支持 `auto`。

## 修复

`server/api/inpaint.js`：`size` 固定传 `'auto'`，不再传算出来的尺寸。

模型自己选分辨率，返回的图尺寸和输入无关（256x576 进去、836x1880 出来）。合成前本来就有"缩回部件原尺寸"这一步，所以下游不用改——**这正是不该改尺寸的原因**：补图必须保持 bbox 不变，骨骼位置是按 bbox 算的。

## 回归测试

`temp/test/inpaint.test.js` 加了两条：

1. `inpaintPart: 发出的 size 必须是 auto，不能是算出来的尺寸` —— 断言请求里的 `size` 字段
2. `editImage: 中转站返回的图尺寸与请求无关时，照样能缩回原尺寸` —— 断言输出回到原尺寸

## 附带修的两处

**错误上报**：原来只取 `body.error.message`，拿不到就退回 `text.slice(0, 200)`。中转站的 400 返回里 `error.message` 恰好就是 `"Bad request"` 这几个字，于是日志里只剩四个字，**状态码也丢了**。现在改成带上状态码 + 完整响应体：

```javascript
const detail = body?.error?.message || body?.message || (text.trim() ? text.trim() : '(空响应体)');
const err = new Error(`HTTP ${res.status}: ${detail}`);
err.status = res.status;
err.body = text;
```

这条修复是后面能定位问题的前提——没有状态码和完整响应体，光看 "Bad request" 无从下手。

**重试**：`RETRY_STATUS = {408, 409, 425, 429, 500, 502, 503, 504}`，最多 3 次，退避 2s → 6s。401/403 不重试（key 不对，重试一百次也不变对）。这次它不是解法，但对真·瞬时故障仍然有用。

# 棋盘格伪透明清除

## 问题

中转站的 `/v1/images/edits` 返回的是 **3 通道 PNG**（`channels=3 hasAlpha=false`），模型无法输出真透明，只能把"透明"画成 RGB 纹理——症状是棋盘格。

实测 3 个补图部件：
- `left_arm.png`: 清除前透明 0px，清除后 48721px，新增透明 32.7%
- `head.png`: 清除前透明 0px，清除后 92403px，新增透明 13.3%
- `right_arm.png`: 清除前透明 0px，清除后 93194px，新增透明 62.5%

## 解决方案

补图返回后立即做一次后处理：从四边泛洪，把与边缘连通的近白中性灰清成透明。

### 为什么用泛洪而不是色键

和去背景一样的理由：角色内部的白（白衣服、白发、白眼珠）和棋盘格同色。全图色键会连内容一起镂空。

泛洪只清"和边缘连通"的棋盘格，内部的白不与边缘连通，保留。

### 检测阈值

- **亮度下界**：R,G,B 都在 237~255（接近纯白）
- **中性灰判据**：通道间最大差 ≤7（排除带色的白，比如淡黄、淡蓝）

实测这两条阈值能准确分离棋盘格和内容区。

### 实现细节

`server/api/inpaint.js` 新增 `removeCheckerboard`：

1. **输入**：RGBA 像素缓冲（4 通道），宽高
2. **泛洪**：四边作为种子（和去背景一致），用显式栈
3. **判据**：每个像素 `min(R,G,B) >= 237 && max(R,G,B) - min(R,G,B) <= 7`
4. **清除**：连通区域 `alpha = 0`
5. **输出**：修改后的 RGBA 缓冲 + 清除像素数

### 接入点

`server/api/inpaint.js:264~290`，在「模型输出缩回原尺寸」之后、「合成到原图」之前插入：

```javascript
// 清除棋盘格伪透明：中转站返回的是 3 通道 PNG，模型把"透明"画成了 RGB 纹理
let filledData = filled.data;
let chkCleared = 0;
if (filled.info.channels === 3) {
  // 转成 RGBA
  const rgba = Buffer.alloc(width * height * 4);
  for (let i = 0; i < width * height; i++) {
    rgba[i * 4] = filledData[i * 3];
    rgba[i * 4 + 1] = filledData[i * 3 + 1];
    rgba[i * 4 + 2] = filledData[i * 3 + 2];
    rgba[i * 4 + 3] = 255;
  }
  const chk = removeCheckerboard(rgba, width, height, 4);
  filledData = chk.buffer;
  chkCleared = chk.cleared;
}
```

只对 3 通道输出做处理：4 通道输出（如果中转站哪天改了返回格式）直接跳过。

### 测试

`temp/test/checkerboard.test.js`，7 个用例全过：

- 场景一：四周棋盘格 + 中间深色内容 → 棋盘格清掉，内容留住
- **场景二（关键）**：角色内部的白不能被删
- 检测阈值：只清近白中性灰（237~255，通道差 ≤7）
- 通道差超标：不是中性灰的白不清（带色的白）
- 连通性：内部棋盘格若与边缘连通则一起清掉
- 四边都能作为种子：背景被角色拦腰切断也能清干净
- 大图不爆栈（用显式栈）

### 数值

实测 `left_arm.png`（259×576）：

- 模型返回：3 通道 PNG，透明区 0px
- 清除后：48721px 透明（32.7%）
- 内容区：白色袖子边缘、高光全部保留，只有边缘连通的棋盘格被清除

### 性能

- 检测 + 泛洪：259×576 约 1~3 ms
- 在整条补图流程（模型调用 20~40s）中可忽略

## 为什么不改提示词

测试过三种提示词变体，包括显式要求"不要画棋盘格"，全部产出 0% 真透明——模型无法输出它，因为响应格式本身没有 alpha 通道。棋盘格是模型对"透明"的视觉表达，编码在 RGB 纹理里。

唯一的解决办法是后处理：把 RGB 纹理检测出来，转成真 alpha。

## 边界

- 只处理 3 通道输出：4 通道输出直接跳过（理论上 4 通道已经有真透明，不需要后处理）
- 泛洪只从边缘出发：内部的棋盘格若不与边缘连通，保留为不透明（这种情况极少见，因为补图的透明区就是边缘）
- 容差固定：237~255 亮度 + ≤7 通道差，实测对所有部件都准确

# 原图带透明度时产物变成不透明（黑框 bug）

## 症状

用户上传一张**已经带 alpha 通道**的图（`test_role_arbg.png`，43.5% 透明），
生成后预览里每个部件都是一块黑框，角色轮廓完全消失，相邻部件糊在一起。

日志看不出问题：10 个部件全部"补图成功"，没有任何报错。

## 根因：补图把蒙版内所有像素的 alpha 写成了 255

`inpaintPart` 的合成循环原本是：

```javascript
if (maskRaw.data[i] > 127) {
  out[i*4]   = filled[i*4];
  out[i*4+1] = filled[i*4+1];
  out[i*4+2] = filled[i*4+2];
  out[i*4+3] = 255;      // ← 元凶
  painted++;
}
```

蒙版的定义是"alpha < 8 的地方"，而**切图为了给关节留拉伸余量，
bbox 四边各外扩了几像素**（`DEFAULT_MARGIN = 4`，界面默认 5）。
那片 padding 在蒙版里同样算"透明"，于是被一起写成了不透明。

结果：每个部件都变成 100% 不透明的实心矩形。实测 14 个部件全部 100%。

## 为什么之前的测试没发现

`temp/test/inpaint.test.js` 里那条断言本身就是错的：

```javascript
assert.equal(await countTransparent(part), 0, '补完不应再有透明像素');
```

它把"没有透明像素"当成了正确行为——而那正是 bug 的定义。
测试和实现犯了同一个错，所以一路绿灯。

## 修复

分成两件事，各管各的：

- **RGB**：蒙版内用模型补出来的颜色（连 padding 一起补，这样网格拉伸时
  取到的是内容而不是透明黑，接缝不泛暗边）
- **alpha**：只允许在"原轮廓外扩 2 像素"的范围内变成不透明

```javascript
const expandable = expandAlpha(base.data, width, height, ALPHA_EXPAND_PX);
// ...
out[i*4+3] = expandable[i] ? 255 : 0;
```

外扩 2 像素是刻意留的：网格在关节处会被拉伸到 bbox 边缘，
那里若全是 alpha=0，转动时接缝直接透出背景。但只开这么一道小口子，
远不足以把矩形填满。

`expandAlpha` 用两遍 Chamfer 距离变换（前向 + 后向各扫一遍全图），
复杂度与半径无关；逐轮膨胀的轮数等于像素数，半径稍大就要扫很多遍。

## 第二个问题：透明区被摊平成黑色，模型照着画了黑块

中转站的 `/v1/images/edits` 内部是 **3 通道**（返回体就是 `channels=3`）。
送进去的 PNG 哪怕带 alpha，透明区也会被按惯例摊成黑色。
模型看到的不是"这里缺内容"，而是"这里本来就有一块黑"——
补出来的自然也是黑块。

修复：送进模型前，先把透明区摊平到**扩散过的边缘色**上
（复用切图那套 `bleedAlpha`，推 8 轮）。模型看到的就是"需要接着画的区域"，
补出来的颜色和周围接得上。

## 附带修好的

`temp/test/inpaint.test.js` 里那条错误断言的注释现在写明了它为什么是错的，
免得以后又被"改回去"。同时新增了"轮廓外扩不得超过理论上限"的断言。

## 测试

新增三层，都能抓住这个 bug（已用"把代码改回旧写法"验证过会失败）：

| 文件 | 层次 | 跑一次要多久 |
|---|---|---|
| `temp/test/inpaint.test.js` | 单测：轮廓像素数、外扩量 | 毫秒 |
| `temp/test/pipeline.test.js` | 端到端（假中转站）：切图 → 补图 → 合成 | 秒 |
| `temp/test/e2e.test.js` | 真流程（真调模型，要 `E2E=1`） | 5~6 分钟 |
| `temp/test/screenshot.test.js` | 浏览器截图 | 20 秒 |
| `temp/test/screenshot-criteria.test.js` | 判据自身的回归（离线） | 毫秒 |

### `temp/test/pipeline.test.js` 为什么必要

`inpaintPart` 的单测用手搓的小图，蒙版边界和 bbox 边界重合，
**看不出"切图外扩的 padding 被一起写成不透明"**。这个测试用真实素材
走完整链路，断言逐行轮廓：

```javascript
assert.ok(grow <= MAX_GROW_PER_ROW, `${c.name} 第 ${y} 行轮廓长了 ${grow} 像素`);
```

旧写法下 torso 的每一行都会变成满宽，差值爆掉，立刻失败。

### `temp/test/e2e.test.js` 的判据是"相对增长"，不是绝对占比

一开始写的是"不透明占比 > 97% 就算不合格"，结果眼镜（99.7%）和
右手（100%）被误判——**它们本来就接近矩形**（眼镜是细长条，
握拳的手是实心块）。判据改成补图前后的增长量，并且上限按**周长**算：

```
允许增长 ≈ 周长 × 2px + π×(2px)²
```

因为小部件周长/面积比大，同样外扩 2 像素，85×118 的靴子能涨 6%，
而 239×354 的裙子只涨 2%。固定百分比必然误伤小部件。

### `temp/test/screenshot.test.js` 的判据踩过两次坑

**坑一：直接数暗色像素占比。** 预览画布本身是深色网格底，
整片都算暗色，角色占多少被淹掉。曾经据此判"74.6% 是黑的"，
其实是背景——**对着一张明确是坏图判了通过**。

**坑二：拿"同尺寸纯色底图"做差。** canvas 是透明的，
透出来的是页面网格而不是纯色，底对不上，差出来全是噪声。

现在用**彩色像素占比**，并且和对照组（藏掉 canvas 截的底图）比：

- 对照组（没画角色）：0.0%
- 坏产物（部件是黑框，把角色盖住）：1.1%
- 好产物：10.4%

差了近 10 倍，门槛卡在 3% 才站得住。
`temp/test/screenshot-criteria.test.js` 专门用两张真实截图守着这条判据，
保证它不会退化成"永远绿"。

## 数值（修复前后对比）

同一个 `test_role_arbg.png`：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 部件不透明占比 | 全部 100%（实心矩形） | 35.7% ~ 100%（按形状） |
| 预览截图彩色像素 | 1.1% | 10.4% |
| 逐行轮廓增长 | 每行到满宽 | 只在轮廓外 2 像素内 |

`level_83/hidden/01.png`（12 个部件的宫灯）真流程实测：
12/12 补图成功，0 失败，轮廓增长全部在理论上限内
（如 `boot_r` +231px，上限 987px）。

## 为什么"输入是透明图"会走到这一步

三个因素叠加，缺一个都不会这么严重：

1. 输入已带 alpha → 去背那步跳过（"图片已带透明通道，跳过去背"）
2. 切图外扩给关节留余量 → bbox 里有真实的透明 padding
3. 补图把蒙版内 alpha 一律写成 255 → padding 变成不透明

如果输入是白底图，第 1 步会先做去背，第 3 步同样会爆；
所以这个 bug 跟"输入是否带 alpha"无关，只是带 alpha 时更容易看出来。

# 测试与交付流程

## 分层

| 命令 | 内容 | 耗时 | 要不要花钱 |
|---|---|---|---|
| `npm test` | 全部离线测试（含截图） | ~20s | 否 |
| `npm run test:shot` | 只跑浏览器截图 | ~20s | 否 |
| `npm run test:e2e` | 真调模型的端到端 | 5~7min | **是** |
| `npm run verify [目录] [源图]` | 产物结构校验 | 秒 | 否 |
| `npm run shot [工程名]` | 只截图，不跑断言 | ~15s | 否 |

`npm test` 默认不含 `test:e2e.js`（它用 `E2E=1` 才启用），
因为一次要花 5~7 分钟和真金白银。

## 为什么必须有"产物结构校验"

单测和端到端都可能漏掉"肉眼一眼就看出来"的问题，因为：
- 单测用手搓的小图，蒙版边界和 bbox 边界重合，看不出 padding 的坑
- 端到端要真调模型，太慢太贵，不可能每次改代码都跑

`scripts/verify-artifacts.mjs` 补中间这层：拿已经生成好的产物，
几秒钟判一次结构是否合理。判据全是相对的（见文件头的注释），
因为绝对阈值在这个项目里反复误伤——

- "不透明占比 > 97% 就是轮廓丢了" → 眼镜 99.7%、握拳的手 100%，
  它们本来就接近矩形
- "近黑 > 35% 就是补图变黑" → 宫灯那张源图本身 17.2% 是纯黑描边，
  灯穗更是 34.8%，那是描边不是黑块

现在用两个量：**直边度**（整行/整列都实心的比例）配**实心度**，
以及**和源图的纯黑占比之差**。

## 截图测试怎么跑起来的

产物目录里只有切图，没有骨架 JSON（骨架是响应里返回的，
落盘的是导出时的产物）。所以截图测试用项目自己的
`generateSkeleton` 从切图重建一份骨架，再塞进 app 的 IndexedDB，
刷新页面走**真实的会话恢复路径**（`restoreSession` → `displaySkeletonInfo`
→ `preview.load`）。这样截的是真实渲染，不是另起一套假的。

`npm run shot [工程名]` 可以直接看效果，产物在 `output/_screenshots/`。

### 注意：`express.static` 只挂了 `./output`

截图测试要求产物在 `./output/<工程名>/` 下。如果生成时把输出目录
指到别处（比如 `/tmp`），`/output/...` 的 URL 取不到图，预览会缺件。

# 预览"重影/叠加"的排查记录

用户反馈：「预览中经常看到有叠加的样的动画图片」。

## 结论：是排查脚本自己的假象，不是 app 的 bug

为了做截图测试，需要从切图重建一份骨架（磁盘上没有骨架 JSON）。
重建时**图省事把每个部件的 bbox 都写成了 `{x:0, y:0}`**——
于是所有部件全叠在画面原点，截出来的图看着就是"同一个东西画了两遍"。

真实的 bbox 来自 AI 分析，同样没落盘。用 `scripts/locate-parts.mjs`
做模板匹配（只匹配 alpha 形状，不受补图改颜色影响）把位置找回来，
吻合度 99%+。接上之后画面就正常了。

**教训**：看到"重影"先怀疑自己的排查工具。这次差点去翻渲染器的绘制循环。

## 顺带确认的（不是 bug）

- **渲染器只画一遍**：`for (const slot of skeleton.slots)` 每个槽位取
  `images.get(slot.bone)` 画一次；生成器给每个部件建一个槽位，
  没有重复的 slot→bone 映射（已断言）。
- **金色的白边**是源图自带的发光描边，不是产物问题（对比源图可见）。
- 早期那次看到的"两个车叠一起"，也是同一个 bbox 假象。

## 新增工具

`scripts/locate-parts.mjs`：模板匹配定位部件。

用途：
- 截图测试/截图脚本重建骨架时，还原部件的真实位置
- 想验证"产物能不能拼回原图"时，直接看吻合度

`npm run shot <工程名>` 配合 `SHOT_SOURCE=<原图>` 使用：

```bash
SHOT_SOURCE=test_assets/level_83/hidden/01.png npm run shot e2e
```

# 输出改成 output/<工程名>/<输入图名>/

## 问题

原来所有产物平铺在 `output/<工程名>/` 下：

```
output/myproj/
├── myproj.json      ← 骨架叫工程名
├── myproj.atlas
├── myproj.png
├── README.txt
└── images/
    ├── head.png     ← 散图叫部件名
    └── body.png
```

一个工程往往对应一整套素材：角色 A、角色 B、道具、特效，各自一张源图。
平铺之后有三处说不清：

1. **看不出谁是谁的**。骨架跟工程名、散图跟部件名，两张源图生成的产物
   除了 atlas 内容之外没有区别，混在一层里只能靠记忆分辨。
2. **重新生成会牵连别人**。清理是扫工程目录，生成角色 A 就顺带把角色 B
   的骨架删了——因为清理逻辑认的是「工程目录里的产物文件」。
3. **`images/` 只能有一个**。两张源图的散图撞名（都有 `body.png`）就直接打架。

## 方案

产物落一层子目录，子目录名跟输入图名：

```
output/myproj/
├── 角色A/
│   ├── 角色A.json    ← 骨架跟输入图名
│   ├── 角色A.atlas
│   ├── 角色A.png
│   ├── README.txt
│   └── images/
└── 角色B/
    └── ...
```

三件套的文件名也跟输入图名（用户选的这档）：`output/我的项目/角色A/角色A.json`。
名对名，从文件名就能看出它属于哪张源图，也符合「一个目录里一套完整工程」的直觉。

**重新生成只清自己那一层**。`cleanSourceDir` 只扫对应的输入图目录，
同工程下别的素材一个文件都不碰——这正是用户要的「不会删除不是自己的目录」。

## 目录算法只有一份

`server/api/workspace.js` 里三个函数，生成、导出、补图重跑、打开目录全走它们：

```js
projectDirOf(outputDir, projectName)              // output/<工程名>
sourceDirOf(outputDir, projectName, sourceName)   // output/<工程名>/<输入图名>
imagesDirOf(outputDir, projectName, sourceName)   // .../images
```

**之前 `exportToSpine` 自己拼了一次 `join(projectDir, 'images')`**，这就是漂移的
起手式：目录算法有两份，改一处漏一处，症状是「生成写进 A、导出读到 B」，
而两边都报成功。现在 `exportToSpine` 直接收最终目录（`sourceDir`），拼路径的
活全归 workspace.js。

`temp/test/workspace.test.js` 钉了这条不变量：

```js
assert.equal(sourceDirOf(root, 'demo', 'teacher'), ws.sourceDir);
assert.equal(imagesDirOf(root, 'demo', 'teacher'), ws.imagesDir);
```

## 输入图名从哪来

`safeName` 一样要过：名字来自前端，写成 `../../etc` 就能让清理和写入跑到工程目录之外。
另外名字是从文件名去掉扩展名来的，中文、空格、括号都正常（`test: resolveSourceName`）。

前端在 `handleFileSelect` 里算一次存进 `currentSourceName`，生成时随表单发上去，
服务端回传规范化后的名字，之后补图、导出都用这个存下来的值——
重跑补图时手里没有文件对象，只能靠它指回原来那个目录。

## 旧产物自动收进子目录

升级前跑出来的 `output/demo/{demo.json, images/}` 会在下一次生成时被搬成
`output/demo/demo/{demo.json, images/}`：

- 用 `rename`：同分区原子操作，中途失败不会留下半份
- **只搬我们自己产出的东西**（产物文件 + `images/`）。用户放在工程目录里的
  参考图、笔记、源文件原地不动——那些本来就不属于某一张输入图，
  搬进哪一层都是错的，还容易让人以为丢了
- 判断依据是「这层还有没有产物文件」，不是「目录是不是空的」。
  光看有没有子目录会误判：用户在工程目录放了 `my-notes/`，
  就会被当成「已经是新结构」而跳过迁移，旧产物永远留在根目录上

**顺序是「先清理、再迁移」**。反过来会白搬一趟：`cleanSourceDir` 清的是目标目录，
搬进去的旧文件会被立刻删掉。先清的语义也更对——这是新一次的产物目录，
旧东西收进来只是为了让它们有个说得清的位置。

## 测试

`temp/test/workspace.test.js` 新增 11 项：

| 断言的 | 防的是 |
| --- | --- |
| 产物落在 `<工程名>/<输入图名>/` | 目录层级拼错 |

| 不碰输入图目录里用户的文件 | 误删用户素材 |

- 新结构产物过 `scripts/verify-artifacts.mjs` 结构校验（轮廓没被糊成实心矩形）

# 设置面板的 key 写入 .env

## 问题

key 只写 `localStorage`。换机器、清浏览器缓存、用 CLI 跑同一个工程，配置就没了，
得重新填一遍。而 `.env` 里的 `ANTHROPIC_API_KEY` 一直是空的。

## 方案

保存按钮写两份：

- `localStorage` → 界面自己用（刷新后输入框里还是那个 key）
- `.env` → 服务端和其他用法用（CLI、换机器克隆下来直接跑）

写 `.env` 失败不阻断：`localStorage` 已经写好了，本次会话照样能用，
只是重启后要重填。所以只提示，不报错。

## 就地改写，不是追加

最省事的做法是往文件末尾追加一行。但 dotenv 里后出现的值覆盖前面的，
于是文件里躺着两行同名 key，**只有最后一行生效**——过两天用户翻 `.env` 想核对，
看到的却是不生效的那行。所以是「就地替换第一处出现的键」。

其余一律保留：注释、空行、键的顺序、缩进风格。`.env` 是用户会手写和手改的文件，
被程序重排一遍会认不出来。我们只动明确要改的那一两行。
值没变就不写文件（省得白改 mtime，也让 `git diff` 干净）。

```js
// 键在原来的位置，不是追加到末尾
assert.equal(lines[4], 'ANTHROPIC_API_KEY=sk-new');
```

## 值只在必要时加引号

key 里出现 `#`（dotenv 当注释起始）或空格（被截断）就必须包起来，
但常见的 URL 和 API key 都是裸写的，一律加引号会让整个文件风格突变。
所以只给真正需要的值加，且写完再读回来必须还原成原值（`test: 往返不被截断`）。

换行、反斜杠、引号同样走转义。

## 绝不回显

写接口的返回值只有 `{ path, changed, created }`——`changed` 是键名列表，不含值。
这个响应会直接进浏览器日志面板，也可能被人截图，key 回显一次就是泄漏，
而且没有任何必要：前端本来就是它自己传上来的。

`.env` 现状接口（`GET /api/api-config`）同理，只报「配了没」和长度：

```js
presenceOf({ ANTHROPIC_API_KEY: 'sk-...' })
// → { ANTHROPIC_API_KEY: { set: true, length: 5 } }
```

设置面板底部据此显示一行提示（「.env 已配置：API Key（35 字符）」），
告诉用户「不填也能跑」。文件里配了、进程里没有时会补一句「服务未重启，本次改动尚未生效」
——dotenv 只在启动时读一次文件。

## 权限与原子性

- 先写临时文件再 `rename`：直接覆写时若崩在中间，用户的 `.env` 会变成半截文件，
  里面可能还有别的服务的配置。`rename` 在同分区是原子的
- 写 `0600`：key 是长期凭证，别让同机器其他账号读到

## 测试

`temp/test/env-file.test.js`，13 项：

| 断言的 | 防的是 |
| --- | --- |
| 就地替换、键不重复、注释与顺序原样 | dotenv 覆盖语义导致「看到的不是生效的那行」 |
| 缺失键追加、值不变时不写文件 | 每次都重写整个文件 |
| `undefined` 不动 / `''` 显式清空 | 空值语义被搞混 |
| 含 `#`、空格、引号的值往返一致 | key 被静默截断 |
| 普通 key 保持裸写 | 文件风格突变 |
| **返回值里不含任何值** | key 泄漏到日志面板 |
| 解析 `export` 前缀、单双引号、行尾注释 | 读回的值不对 |

## 实测

真实服务上：保存 → `.env` 里 key 和 baseURL 都写进去了、`PORT` 还在、
只有一行 key、响应和配置接口都没有回显。测完把 `.env` 还原。
