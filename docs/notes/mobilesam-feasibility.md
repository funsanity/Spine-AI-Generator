# MobileSAM 可行性分析（本机实测）

> 测试日期：2026-09-18 · 机器：Apple M2 Pro / 16GB / macOS 26.5 · 项目：spine-tool-v1
> 结论：**可行，建议引入，但只用在"打轮廓"这一步**，不改动现有切割/补图/装配流程。

## 一句话结论

MobileSAM 在 M2 Pro 上从进程冷启动到出图 **2.07 秒**，掩码质量比现役的"让 Claude 输出多边形顶点"高一个量级 ——
12.png 的番茄从 20104px 的"番茄+篮圈+提手"降到 7720px 的**纯番茄**，且被提手挡住的弧带自动留成透明，
正好是补图该接手的输入。**现役 6 个部件里 4 个切图混带邻件的问题，它一次解决。**

## 3. 启动与运行流程

### 完整链路（实测）

```
import torch/PIL       0.66s
import mobile_sam      0.79s
加载权重 + 搬到 MPS    0.33s
首次编码（图编译）     0.40s   ← 只在第一次贵
─────────────────────────────
到第一张掩码           2.07s   （两次独立测试：2.07s / 2.06s，稳定）
```

### 运行期开销（关键：与分辨率无关）

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 图像编码 | **0.08s**（热） | 每张图**一次**，所有部件复用，300px 与 1024px 相同 |
| 单部件解码 | **10–25ms** | 每个部件一次，6 个部件合计 ~0.15s |
| 常驻显存 | **61 MB** | 对 16GB 机器无感 |

**这是 SAM 类模型最重要的架构特性**：编码贵、解码便宜，且编码只与"图片张数"有关，与"部件个数"无关。
所以哪怕一张图切 20 个部件，总开销也只比切 5 个多零点几秒。

### 与现役流程的衔接

现役链路是 `Claude 分析 → cutImageParts（Node）→ 补图`。
MobileSAM 只替换其中"部件轮廓从哪来"这一环：

```
Claude 分析（照旧，输出 bbox + depth + 名称）
        ↓  把 bbox 当提示喂给 SAM
MobileSAM → 每个部件一张像素级掩码
        ↓  掩码 ∩ 源图不透明像素
cutImageParts 按掩码裁切（替代原来的多边形填充）
        ↓  被遮挡区域留透明
补图（照旧）
```

Node 调 Python 走子进程即可（项目里 `scripts/auto-improve.mjs` 已有 `spawn` 的先例）。
**建议常驻一个 Python worker 进程**：2.07s 的冷启动摊到每次生成太浪费，
常驻后单张图总成本 ≈ 0.08s 编码 + 0.15s 解码 = **0.23 秒**，比现在等 Claude 分析（几秒到十几秒）小得多。

## 5. 为什么它治得了这个病

现役方案的结构性缺陷：

```
多边形顶点（Claude 给）→ 截取 → 深度擦除补救
```

问题出在第一环：**让语言模型报顶点，它倾向于把"细弧压在大色块上"的边界整块划给大色块**。
提手压在番茄上时，Claude 报的番茄多边形把整条提手包进去了。后续的深度擦除是补救措施，
但擦除依赖深度判断正确 —— 判断错了就擦不干净。

MobileSAM 的掩码**天然只包含这件东西可见的像素**：

```
掩码 → 截取 → 完成
```

提手压在番茄上的那条弧，**天然不在番茄掩码里**。不需要深度推理，不需要擦除。
被挡住的部分留成透明 —— 这恰好就是补图需要的输入格式。

换句话说：**现役是"先切脏了再擦"，MobileSAM 是"一开始就不脏"。**

## 6. 提示（prompt）策略：用框就够，但要注意两点

实测三种提示方式：

| 方案 | 未覆盖源像素 | 说明 |
|---|---|---|
| 纯框 | 6.7% | **推荐**，最简单 |
| 框 + 正样本点 | 7.7% | 无改善 |
| 框 + 点 + 只留连通块 | 7.9% | 无改善 |

**结论：纯框（`predict(box=...)`）就够，不必加点。**

两个必须注意的坑：

1. **不要用框中心当种子点**。提手是空心的，框中心落在洞里（那是透明背景），
   实测空心提手的掩码会掉到 **2px**。如果将来要用点提示，
   种子应取"多边形内距边缘最远的像素"（`scripts/mobile-sam-prompt-compare.py` 里的 `_seed_point` 已实现）。

2. **"互相重叠"不是好指标**。提手压在番茄上，两件物品在源图里本来就占据同一片像素区域，
   两件掩码都覆盖这块是**正确的**。实测重叠 23076px，绝大多数是真实遮挡而非错误。
   判定质量要看**切图本身**，不要看重叠面积。

## 7. 残留问题与已知边界

1. **AI 的 bbox 贴太紧会漏掉 1–2px 抗锯齿描边**（实测漏 2748px / 6.7%，
   集中在篮子外轮廓）。但**放宽框会灾难性失控**，实测：

   | 扩框 | 未覆盖 | 番茄 | 篮背 | 篮前 |
   |---|---|---|---|---|
   | 0%（原框） | 6.7% | 7720 | 18486 | 15401 |
   | 3% | 51.2% | 7804 | **2** | **6** |
   | 5% | 50.9% | 8234 | **0** | **8** |
   | 20% | 5.5% | **13795** | 0 | 18114 |

   框一放宽，SAM 就跳到别的东西上 —— 篮背/篮前的掩码直接归零，
   番茄掩码反而涨到 13795px（把篮子吃进来了）。
   20% 那行覆盖率看着"恢复"到 5.5%，其实是番茄膨胀后顺带盖住了篮子
   的像素，是虚高，不是变好。
   → **保持 AI 原框不动**，靠补图/边缘扩散补那 1px 描边。

2. **框里塞两件东西时会出错**。SAM 会挑"框里最主要的那件"。
   这依赖 Claude 给出的 bbox 质量 —— bbox 太糙时 SAM 也会跟着错。
   （但即使框略糙，SAM 仍远好于多边形方案，因为它的边界是像素级的。）

3. **移动端 / 其他机器未验证**。本次只测了 M2 Pro。
   CPU 路径也测了（0.31s 编码），比 MPS 慢 4 倍但**依然可用**，
   所以没有 Apple GPU 的机器也能跑，只是慢些。

4. **完整性风险**：MobileSAM 是 2023 年的模型，最后推送 2026-05。
   若不是长期维护项目，建议把权重文件纳入自己的存储，别只依赖上游链接。

### 它怎么自动启动的

用户什么都不用做。生成流程走到切图那一步时：

1. `segmentParts()` 先查环境（只看文件在不在，不 import torch——那要一秒多）
2. 在 → 让 client 拉起 worker；worker 加载完模型会发 `{"ready":true}`，客户端等的是这个信号，不是 sleep
3. 不在 → 记一条日志告诉用户怎么装，返回 null，**生成照常往下走**

worker 之后就常驻了，同一张图重复切只编码一次。空闲 10 分钟自动关掉把内存还回去，
下次要用再拉起来（约 2 秒）。

## 9. 角色图实测与「覆盖率兜底」（2026-09-18 补）

前 8 节的所有数据都来自**一张**图（`test_assets/level_83/hidden/12.png`，静物篮子）。
换成角色图 `test_assets/test_role_arbg.png`（298×838，卡通女孩）后暴露了新问题，
下面是修法和定标。

### 9.1 问题：掩码塌成碎片

部件和邻件贴合、或者一个框里塞了两件东西时，SAM 不是"切得糙一点"，
而是**只圈出一小块碎片**。实测那张角色图：

| 部件 | 掩码盖住框内不透明像素 | 切出来的东西 |
|---|---|---|
| `left_arm` | 5.4% | 一小团手掌，整条袖子没了 |
| `right_arm_scissors` | 3.7% | 同上 |
| 其余 7 件 | 35.2%~79.9% | 正常 |

失败的和正常的中间隔着 **30 个百分点**，很好分。

这里有个反直觉的点值得记下来：`multimask_output=True` 会回 3 个候选，
`argmax(scores)` 挑的那个**面积可能很大**（实测有 15530px 的候选），
但 `_largest_component()` 是在挑完之后才跑的 —— 大而碎的候选被收敛成一小块。
所以"挑面积最大的候选"治不了这个病（实测加了 `DEGENERATE_RATIO` 启发式，
0.0 和 0.4 两档在 9 个部件上输出**逐字节相同**，已回滚）。

### 9.2 修法：覆盖率兜底，按部件退回多边形

worker 每张图顺手算一次源图不透明区域，解码时给每个掩码带一个 `coverage`：

```
coverage = (掩码 ∩ 框内不透明像素) / 框内不透明像素
```

分母**只取框内、且只取不透明处**。两个都不能省：
框外的东西本来就不该算；透明背景也不该算，否则细长部件的分母里塞满空白，
覆盖率永远很低。

`server/sam/segment.mjs` 里 `MIN_COVERAGE = 0.15`，低于它的掩码**逐个删掉**，
那个部件退回 AI 多边形，其余部件照用 SAM。全删完才返回 null。

**为什么不用别的指标**（都试过，都是坑��：

- *互相重叠*：提手压在番茄上时两张掩码都覆盖那片区域，这是对的。§6 已记。
- *包含关系*：`hair_bun` 100% 落在 `head` 里、面积差 12.8 倍，但它是**正确**的掩码。
- *被遮挡就是失败*：分母只算框内不透明像素，被前方部件挡住的地方在源图里
  依然不透明，所以真被挡很多的部件覆盖率也不会低到 15% ——
  `hair_bun` 整块只有 2353px，覆盖率照样 41.9%。

### 9.3 浏览器端到端对照（同一条 UI 路径，只切开关）

用 Playwright 真的走一遍网页：上传 → 填提示词 → 展开「5. 网格与补图」→
切「像素级部件分割（MobileSAM）」→ 生成，等的是 `/api/generate` 的响应本身。

> 踩过的坑：日志面板是**全局广播**的，用户自己开着的页面也在往里写。
> 拿日志文本判"跑完了没"会被别人的行误伤（被一条「[导出] 图集打包失败」
> 里的"失败"骗得提前关掉浏览器）。权威信号只有那个 HTTP 响应。

开关打开那轮的日志（原样）：

```
⚠ 这几个部件的掩码几乎是空的，改用多边形轮廓：left_arm(7.2%)
✓ 分割完成：8/9 个部件，耗�� 1.13s，平均置信度 0.87
✓ 切图完成：9/9 张图片
✓ 其中 8 个部件用了 SAM 像素级掩码，1 个用多边形轮廓
```

**判定指标：把切图按 bbox 贴回原画布，看每个部件认领了自己框内多少内容。**
（先验证过贴回的偏移：9 个部件的命中率都是 100.0%，位置没错，
所以"无人认领"是真的没人认领，不是对位错了。）

| 部件（同一个身体部位） | SAM 开 | SAM 关（多边形） |
|---|---|---|
| body | **56.6%** | 5.0% |
| head | **96.5%** | 39.0% |
| hair_bun | **55.0%** | 49.1% |
| glasses | 32.1% | **69.2%** |
| left_arm | 12.2%（已退回多边形） | 19.1% |
| 右臂+剪刀 | **44.9%** | 4.3% |
| apron | 67.2% | **77.3%** |
| 裙摆 | **40.7%** | 17.2% |
| 鞋/脚 | 38.3% | **53.2%** |

整图合成回去：**SAM 覆盖 69.9%，多边形 65.1%**。
多边形那条路才是坏得更厉害的那条 —— `body` 只认领自己框内 5.0%、
右臂 4.3%，也就是"整个躯干和手臂几乎是空图"。

### 9.4 还没解决的

1. **`glasses` 会切成整张脸**。三个候选掩码全是脸部区域（7102~9919px），
   没有一个是细镜框。覆盖率 77.3% —— 掩码确实盖住了框内的不透明像素，
   只是**盖的是错的东西**，所以 9.2 的兜底既抓不到也不该抓它。
   这是 §7.2「框里塞两件东西」的具体一例。**不是回归**：多边形那条路
   切出来是"脸 + 一块多余的斜角"，也不对。
2. **两条路都有厚缺失区**。腐蚀 3 轮后仍存在的最大缺失块：SAM 16603px、
   多边形 20527px，位置都在右侧手臂一带。

   > **这一条的归因当时是错的**，原文说「AI 的 bbox 没枚举到的部位谁都认领
   > 不了，这是分析环节的边界」。真正的原因是流程里少了一层：没有任何一层
   > 持有「没被任何轮廓圈中」的残料。已修，见 §10。

## 10. 底板与绘制顺序（2026-09-19 补）

§9 里记了一句「两条路都有厚缺失区……AI 的 bbox 没枚举到的部位谁都认领不了，
这是分析环节的边界，不是分割环节的」。**这句话是错的**，至少是把病因归错了。
真正的原因是流程里少了一层，跟 bbox 准不准无关。

### 10.1 病因：没有任何一层持有「残料」

现役流程只产出部件切图。每个部件的轮廓（SAM 掩码或 AI 多边形）都只覆盖它
自己那块，于是源图上**没被任何轮廓圈中的像素就彻底消失了**——不在任何一张
切图里，拼回去也拼不出来。

实测 `test_assets/test_role_arbg.png`（298×838）：

| | 部件并集覆盖源图不透明像素 | 丢失 |
|---|---|---|
| SAM 路径 | 59.1%~69.9% | 30~41% |
| 多边形路径 | 65.1% | 34.9% |

数字每轮略有浮动（AI 每次给的 bbox 不同），但量级稳定在**丢掉三到四成**。
领口、腰侧、鞋跟旁边那些零碎，AI 不会单独报成部件，谁都不认领。

### 10.2 修法：底板（`server/api/baseplate.js`）

```
底板 = 源图 - 所有切图的并集
```

放在所有部件**后面**（`depth = -1`，槽位排第一个），于是

```
底板 ∪ 全部部件 ≡ 源图不透明像素
```

按构造成立，不依赖任何轮廓质量。轮廓再差也只是「这块像素归底板还是归部件」
的分配问题，不会再丢东西。实测覆盖率 **59.06% → 100.00%**，0px 丢失、
0px 画布外多余、与部件 0px 重叠（补图前）。

两个实现上必须这样做的点：

1. **并集从落盘的切图算，不重算掩码**。切图经过掩码裁剪、深度擦除、剪影吸附
   好几道处理，重算很容易和实际的 PNG 不一致——一旦不一致，底板就会和部件
   重叠（同一块像素画两遍，动起来穿插）或者留缝（还是丢内容）。
2. **必须在补图之前算**。补图会往洞里填颜色、改 alpha，那之后再算「部件认领了
   哪些像素」就不准了。

底板上被部件挖走的地方是洞，顺手写一张 `_base_plate.erased.png`——
补图那边本来就认这张掩码，用它区分「部件外的留白」（保持透明）和
「该填实的缺口」（洞连不连到图边都不影响，正是这张掩码存在的理由）。
实测 94424px 的洞补图填了 100%。

### 10.3 顺带挖出来的真 bug：绘制顺序没按 depth 排

加了底板之后量默认姿势的合成图，发现**不开补图时逐像素等于源图**（偏差 0.00），
一开补图就冒出 16.34% 的像素偏差 >40。归属统计一跑就定位了：
23029px 偏差像素里 **22981px（99.8%）** 都是 `right_arm_scissors` 画的，
而且是它那些「被前方部件挖掉、由补图按推断填回来」的像素。

病因：`generateSkeleton` 里骨骼和槽位共用同一个顺序（拓扑序）。

- 骨骼**必须**拓扑序：父在子前，否则子骨骼算不出相对偏移。
- 槽位顺序**就是绘制顺序**，和「谁压在谁上面」是另一回事。

沿用拓扑序的后果：`left_arm` / `right_arm_scissors` 是 depth 1
（在 depth 2 的围裙、depth 3 的眼镜后面），却排在它们之后绘制，
于是手臂补出来的推断内容盖住了围裙和眼镜真正可见的内容。

修法是槽位单独按 depth 稳定排序（depth 相同保持拓扑序，缺 depth 当 0）。
**偏差 23029px → 48px（16.34% → 0.03%），平均偏差 9.06 → 0.06/255。**

这个 bug 和底板无关，只是因为底板把「合成回去应当等于源图」变成了一条
可判定的断言，它才暴露出来。

### 10.4 「补的是推断内容，不是把部件抄回去」怎么验

用户的要求是：洞要按形状补，但**不能把部件的颜色抄回去**——抄回来等于把
部件画了两遍，部件一动就露出一个它自己的残影。

第一版判据「和源图逐像素相同的比例」是**错的**，量出来 35.7%，看着像抄了。
这张图是扁平色卡通，躯干、裙子都是大片纯色，纯色区里「按四周推断」和
「原来的颜色」本来就是同一个值，相同不能说明抄。

正确判据是按源图局部梯度拆开，只看**细节区**（剪刀、镜框、五官这类有结构的
地方），再加一个独立量：底板自己的细节强度。实测（只取「只被一个部件认领」
的 41952px，也就是该部件一走底下只剩底板的那些像素）：

```
底板在这里是空的          0px（0.00%）   ← 动起来不会破洞
平坦区与源图相同          47.2%          ← 纯色区相同是正常的
细节区与源图相同          10.1%          ← 低，没把结构画回去
细节区平均梯度  源图 75.5 / 底板 41.6    ← 底板明显更平，是推断的
```

还踩过一次同类的坑：把「部件挪开后露出的全部像素」拿来比，细节区 80.6% 相同，
一度以为是残影。归属统计后发现那片区域里 1205px 是 `left_arm`、901px 是
`apron` **自己切图里就有的真内容**——`right_arm_scissors` 那轮退回了多边形，
多边形很粗，把邻件的像素一起圈进了自己的切图。邻件当然也持有那些像素
（本来就是它们的），所以那里「和源图相同」是**正确**，不是抄。
**判据必须限定在「底板是唯一垫底者」的像素上。**

## 12. 底板补图黑块守卫（2026-09-19 补）

### 12.1 现象

用户目视测试发现底板上有黑块。定位：`output/blackfix_verify/test_role_arbg/images/_base_plate.png`
里，源图中灰（lum 64–80）的位置，底板补出来是 rgb(0–19)。

### 12.2 第一轮修法：nearBlack 守卫

`resolveHoleFills` 原本只抓「四周亮、洞里却白」的情形。新增对称判据：
四周亮色（ring max > 40）时，洞里的近黑（max ≤ 25）同样算补砸，替换为环均色。
实测底板 6044px 黑块降到 987px（−83%）。

同步加了 `depthGuard` 参数：底板补图时把 `erased` 掩码传进来，
被深度擦除挖走的位置不许当参照色来源，避免跨层颜色污染。

### 12.3 剩余 987px 的根因

追踪那个 7952px 的连通洞：
```
ring = rgb(29,22,33)   max = 33   → ringIsDark = true（max ≤ 40）
洞内填色 max = 0–25   → nearBlack = true
```

老代码的 `ringIsDark` 分支假设「四周暗 → 近黑填充是对的」，于是跳过黑块替换。
但 ring max=33 并不是近黑（nearBlack 门槛是 ≤ 25）。填色 max ≤ 25 明显比参照色更暗，属于补砸。

### 12.4 第二轮修法：medium-dark ring 也要纠黑

把 `ringIsDark` 分支里的"ring 本身近黑"单独拆出来：

```js
const ringIsNearBlack = Math.max(...ring) <= 25;
const badN = whiteN + (ringIsNearBlack ? 0 : blackN);
if (badN / cells.length > 0.25) {
  for (const i of cells) fallback[i] = ring;
} else {
  for (const i of cells) {
    if (nearWhite(filledData, i) || (!ringIsNearBlack && nearBlack(filledData, i))) fallback[i] = ring;
  }
}
```

规则：
- ring max ≤ 25（真近黑）：近黑填充正常，只纠近白。
- ring max 26–40（中暗）：填色比参照更暗就是补砸，近黑也要替换。

### 12.5 验证

离线对现有 `blackfix_verify` 底板跑修补后的逻辑：

```
erased + 底板黑（max≤25）+ 源图亮（lum>40）: 987px
  → 修补后全部替换：987px（100%）
  → 剩余：0px
```

回归测试 8 条（含 2 条新增 medium-dark ring 用例），全部通过：
- ring 中暗（max=33）、洞里近黑 → 替换为参照色 ✔
- ring 真近黑（max=20）、洞里近黑 → 保持不动 ✔

## 13. 中转站瞬时 400：AI 分析失败（2026-09-19 补）

### 13.1 现象

生成流程跑到最后一步失败：

```
✗ 生成失败: AI 分析失败: 400 {"type":"error","error":{"type":"invalid_request_error",
  "message":"Invalid request"},"request_id":"task_2bd73006593247d2ad93af27e7d6356e"}
```

来路是 `server/ai/claude.js` 的 `analyzeImage`。前面去背、补图（8 个部件、
181 秒）都已经跑完，卡在 AI 分析这一步，整轮白跑。

### 13.2 排查

逐项排除，请求体本身没有问题：

| 变量 | 试的值 | 结果 |
|---|---|---|
| max_tokens | 100 / 8192 / 12288 | 全部成功 |
| 提示词长度 | 短 / 12k 字符 / 真实 5288 字符 | 全部成功 |
| 图片大小 | 298x838 (331KB b64) / 150 / 75 宽 | 全部成功 |
| thinking | 开（budget 4096） | 成功 |
| 图片编码 | 原文件 / sharp 重新编码 | 全部成功 |
| 同请求连发 | 6 次 | 前 5 次全部成功 |

结论：**中转站的间歇性抖动**。同一个请求、同一张图，隔几秒重发就过。

顺带发现 `.env` 里的 `ANTHROPIC_MODEL=claude-opus-5[1M]`（以及
`ANTHROPIC_DEFAULT_*_MODEL` 一族）是中转站**不认**的模型名，会明确报
`No active provider route for TEXT/claude-opus-5[1M]`。本应用不读这些变量
（`grep process.env.ANTHROPIC_MODEL server/` 无结果），是别的工具留下的，
与本次故障无关。

### 13.3 根因

代码里没有任何重试。Anthropic SDK 默认只对 429 和 5xx 重试，**400 直接抛**，
于是一次瞬时抖动就让整个生成流程失败。

### 13.4 修法

`server/ai/claude.js` 增加 `createWithRetry`，只包 `messages.create`：

```js
const RETRY_MAX = 2;          // 最多再试 2 次，合计 3 次
const RETRY_BASE_MS = 1500;   // 退避：1.5s、3s
```

判断哪些错误值得重试（`isTransient`）：

- **重试**：429、5xx、连接层抖动（ECONNRESET / ETIMEDOUT / ENOTFOUND …）、
  以及文案是 `Invalid request` 的 400（实测是瞬时抖动）。
- **不重试**：401/403 鉴权失败、模型名不存在（`No active provider route`）、
  其他请求体不合法。这些重试多少次都一样，早点报错省时间。

`createWithRetry` 的第三个参数是退避基数，默认 1500ms；测试传 1ms，
避免为了跑测试真等十几秒。

### 13.5 验证

`temp/test/ai-retry.test.js`，13 条：

- `isTransient` 的 7 条分类判据（429/5xx/连接层/瞬时 400 要重试；
  401/403、模型名不存在、未知错误不重试）
- `createWithRetry` 的 6 条行为：首次成功只调一次、两次失败后第三次成功、
  重试用尽抛最后错误且不超次数、不可重试错误立刻抛出、
  模型名不存在立刻抛出、重试时原样重发同一请求体

### 13.6 复现

```bash
node --test temp/test/ai-retry.test.js          # 13 条
node scripts/repro_analyze_400.mjs         # 变量隔离：四组请求体全部成功
node scripts/repro_analyze_real.mjs        # 真实提示词；含 [1M] 模型名对照
node scripts/probe_image_size.mjs          # 图片尺寸/编码对照
```

## 14. 同一块内容进了多张切图 / 谁都没画（2026-09-19 补）

用户报的原话：「一个部位在很多张图上都会出现，比如在输入 test_role_arbg.png 中
头部在多个部件都有，组成 spine 动画的时候，看到头部在断裂滑动，很不符合实际。」

渲染成动画量了一下，是**两个方向相反**的缺陷叠在一起，都得修。

### 14.1 掩码重叠 → 重复

SAM 给每个部件独立预测，掩码之间会重叠。原代码有一条豁免
「本部件的 SAM 掩码认领的像素不让位」（`cutter.js` 深度擦除那一步），
本意是防擦空（早先实测 `left_arm` 只剩 4.3% 不透明）。副作用是：
`body` 的框圈住整个躯干，掩码很容易把头颈一起认领进来，豁免一生效，
头的像素就在 `body` 上留了一份，`head` 自己也有一份——同一块内容挂在两根骨头上。

**改法**：建一张归属表 `ownerOf`，一个源像素只归**认领它的、depth 最大的**那个
部件（depth 大 = 靠前 = 实际可见的那一层）。depth 打平时按掩码面积小的优先
（更具体），再平按名字（只为了可复现）。让位的像素记进 `yieldedMask`，
并进 `erasedMask` 交给补图。

实测 `test_role_arbg`：重复像素比 **58.3% → 6.0%**。剩下 6% 全来自
polygon-only 部件对（`left_arm` / `right_arm_scissors` 掩码置信度不足被退回
多边形），归属表不管它们，行为不变。

### 14.2 掩码漏掉 → 谁都不画（这条才是"头转身不转"的真凶）

MobileSAM 是**纯框提示**（`worker.py` 只传 box，取 `argmax(scores)`）。
喂一个「头」的框，它回来的是**头发**：实测 `head` 掩码只盖住框内
**32.5%** 的不透明像素（7585px），脸、下巴、耳朵、眼镜全在掩码外。

那些像素于是三种去向：
- 一部分被 `torso` 的掩码认领（两个框有约 100px 重叠带）
- 剩下的**谁都不认领**，不进任何切图
- 补图又按「透明区连不到图边才算洞」的规则，把它们当**外部留白**保持透明

结果就是头转了，脸留在原地不跟着动。

**改法**：框既是 SAM 的提示，也算一次**声明**。框里没被任何掩码认领、
且源图有内容的像素，归**框面积最小**的那个部件（声明更具体）。
实测这张图有 24327 个这种像素，其中 21083 落在某个部件的框里——
`head` 分到 12269px，`torso` 5262px，`left_arm` 1141px。

**关键的一个坑**：认回来还要在 SAM 裁图那一步**放行**。原来的 clip
无条件删掉「掩码外」的像素，会把刚认回来的又删掉。归属表看着完全正确、
切图却仍然透明，得逐像素插探针才看得出来。现在 clip 里加了一条
`if (ownerOf[si] === name) continue;`。

**2026-09-19 补：这条放行只写在 SAM 分支里，polygon 分支漏了。**

`right_arm_and_scissors` 的 SAM 掩码几乎是空的（占框内 11.0%），被降级到
polygon 路径；可那份小掩码仍然参与了归属表、把框内像素判给了它，然后
polygon 那句「轮廓外的删掉」又把它们全删了。17416px 有内容却谁都没画，
渲染出来手臂中间一串竖直白碎片。SAM 分支早就有这条规则，polygon 分支
照着补上了：

```js
if (ownerOf && ownerOf[srcRow + x + x0] === name) { keptByBox++; continue; }
```

**2026-09-19 还补了第三遍认领：连通性。**

前两遍（掩码、按框）都建立在「AI 给的框圈住了这个部件」这个假设上。
假设不成立时就漏：实测 role11 那轮 AI 只给了 `right_arm_with_scissors`，
框 x102..237 **只圈住剪刀**，右臂那条袖子整条在框外——14646px 谁都认不了。
而 role10 那轮同一个素材给了 `right_arm_and_scissors`、框 x150..285
圈住了袖子。**同一个素材、同一个模型，两轮的框不一样**，靠调 prompt
解决不了。

框是 AI 的估算，**内容自身的连通性比框可靠得多**：袖子在源图里和手臂
是同一块不透明区域，沿着它泛洪就能找到手臂。从每个「源图不透明、还没归属、
且不在任何框内」的像素出发，泛洪**整片不透明连通区域**，碰到已有归属的
像素就记一票；整块区里谁票最多就归谁（平局按 depth 深、再按名字），
只把「不在任何框内」的那些像素真正写走，框内的留给第二遍。

两个实现坑，都踩过：

1. BFS 的 `seen` 是全图共用的已访标记，**不能用它当"这块是谁的"**——
   第二块会把第一块一起写进去。块内像素要单独收进一个数组。
2. **泛洪范围不能只限"无主像素"**。第一版只穿过无主像素、穿过时不投票，
   于是肘部那块**自己内部没有已归属像素**可投，`votes` 为空直接跳过，
   剩 5.85% 框外孤儿。必须能穿过框内那部分已归属像素才投得出票。

**这个缺口是从渲染视频里肉眼发现才补的**：前面所有断言全绿，因为它们量的
都是"画了什么"，没人量"漏了什么"。现在 e2e 有 `checkCoverage()` 兜着，
但**判据后来换掉了**（下面 14.6 说明为什么它不能当门槛）。

| 素材 | 孤儿（修前） | 修后（判据换成"内容漏失"之后） |
|---|---|---|

| test_role_arbg | 24134px (17.12%) | 0px (0.00%) |

1. **e2e 根本没走 SAM**。`runPipeline` 直接 `cutImageParts(...)` 不传 `samMasks`，

   那个绿勾是假信心。现在补上了 `segmentParts` 并把掩码落盘到 `_temp/masks/`。
2. **失败的那一轮什么证据都不留**。诊断数据以前写在断言之后，一失败就全丢，

### 14.5 认领对了不等于画得出来（窗口要跟着撑）

14.2 的连通性认领修完，日志确实打出「⊹ 连通性认领 12619px 落在所有框外」，
可切图**仍然漏掉源图内容的 6.76%**，集中在左袖外沿、发髻边、裙摆两侧、
小腿——全是长条部件的外轮廓。

原因不在归属表，在**窗口**：切图窗口是「AI 的框 ± margin」，而认领到的
那片像素**本来就在框外**。归属表判给它了，窗口没装下，一个像素都画不出来。
认了白认。

修法是按归属表把窗口撑到"这个部件真正拥有的内容"的范围（`growCap`，
单边上限 120px，防止误认的像素把窗口拉爆）。加了个可关闭的 `growCap: 0`
做 A/B：

| test_role_arbg | 内容漏失 |
|---|---|
| `growCap: 0`（只认领、不撑窗口） | 9526/140936px = **6.76%** |
| 默认（撑窗口） | 0/140936px = **0.00%** |

12.png 两种都是 0.00%（它的内容基本都在框内，本来就没这个问题）。

### 14.6 判据本身又错了一次：窗口撑开后不能再用框来判

`checkCoverage` 把"框外孤儿"当硬指标（`outsideBoxOfSrc < 0.08`）。
窗口一撑开，这条**必然接近 0**——框就是照认领范围撑的，怎么切都合格。
一扇假门。

更糟的是它还**误报过**：`checkCoverage` / `checkGhosts` / `checkDuplicates`
三处都拿 `verify-input.json` 里 `parts[].bbox`（AI 的框）去把切图贴回源图
坐标，而窗口已经撑开，两者差几十像素（role 实测 body 188x630 vs 211x640）。
于是 role 报了 9.78% 孤儿、判红，**实际是整张图错位贴出来的幻影**。

两处一起改：

1. 窗口位置改用 `bboxActual`（切图自己回的 bbox，和 PNG 尺寸逐像素对得上），
   三个 `check*` 统一走 `boxOf()`。
2. 断言换成 `checkMissingContent()`：只问"源图这块内容有没有人画"，
   **不经过任何 bbox**。位置取错会把结果算错，不会算对——所以它当门槛
   比"框外孤儿"可靠。阈值 1%。

顺带把阳性对照补上：单测里把 `growCap` 设成 0，那条断言立刻变红
（`temp/test/part-isolation.test.js` 的「内容落在所有框之外时…」）。

### 14.7 断言本身也修了一次：什么叫"padding 被填实"

掩码修完，e2e 仍然红，报 `apron 2393px`、`right_arm 869px`「落在擦除区之外的
留白上」。看着像补图把外扩的 padding 填成了不透明，但那轮的数字和上一轮
对不上（同一部件 2393 → 175），先怀疑是量法有问题。

写了个分类脚本逐像素复核（新增不透明、不在 erased 掩码内的像素），
按 8 邻域分类：

| 部件 | 不在 erased 里的新增 | 内部孔洞 | 孤立块 |
|---|---|---|---|
| hair | 240 | 240 | 0 |
| apron | 175 | 175 | 0 |
| hand_scissors | 91 | 91 | 0 |
| left_arm | 25 | 23 | 0 |
| right_arm | 12 | 12 | 0 |
| body / head / skirt / 两只鞋 / glasses | 0 | 0 | 0 |

**一个 padding 泄漏都没有**。那些像素全部是**内部孔洞**（四周 8 邻域都是
已不透明的内容）。补图的 alpha 放行规则本来就是「连不到图边的透明区才填实」，
部件接缝处的缝填上是对的。它们之所以不在 erased 掩码里，是因为擦除掩码记的是
「深度擦除挖走的」，而孔洞是源图本来就透明的——两码事。

所以旧断言的口径错了三处：

1. **把"不在 erased 掩码里"当成可疑**。孔洞本来就不在掩码里。
2. **把"补图前透明"当成"那儿本该透明"**。补图前透明的原因可能是被 SAM 裁掉、
   被归属让位（14.1/14.2），两者都该填。实测 body / head / skirt 这些被擦得
   最狠的部件，新增像素反而是 0——因为它们的新增全落在 erased 掩码里。
3. **按像素计数，不看形状**。padding 被填实是个**形状**问题：那片矩形离轮廓
   有几十像素，一旦被填，长出来的第一块必然四面皆空。而补缝长出来的像素
   总数可能很少（12px），也永远贴着轮廓。

改成**连通性判据**：对可疑像素做 8 邻接连通块标记，任一块只要有一个像素
挨着「补图前就不透明的」内容（或擦除区），整块算贴着轮廓长出来的，合法；
整块都不挨任何依托的才算悬空。实测 11 个部件新增块 39/16/5/2…，**悬空 0px**。

这条判据同时扛得住那个回归复活：真漏了 padding，被填的面积是整片矩形、
且不与轮廓相连，一定报出来。

### 14.8 最后一轮 e2e 又栽在别的地方：输出被 max_tokens 截断

改完上面这些，12.png 的 e2e 全绿（重影 0.00%、内容漏失 0.00%、
悬空新不透明 0px），role 那一轮却**连切图都没走到**：

```
[AI] 响应文本: { "parts": [ { "name": "legs_boots", … "polygon": [
  {"x": 0.175, "y": 0.875}, …, {"x": 
[AI] 解析失败: SyntaxError: Expected ',' or ']' after array element in JSON at position 1109
```

停在最后一个顶点中间，`stop_reason` 是 `max_tokens`——**输出被截断了**。

这条错让整轮白跑：去背、SAM、切图、补图（实测 156s、真金白银）全做完了，
卡在最后一步的 `JSON.parse`。而且它会伪装成"代码回归"——第一次看到
`Expected ',' or ']'` 时我以为是 `parseResponse` 改动引入的 bug。

`createWithRetry` 之所以没兜住，是因为它只包 `client.messages.create`，
而截断是**成功响应**，API 不报错，压根不进那个 catch。

修法：`parseWithRetry()` 捕获解析失败后，**只看 `stop_reason === 'max_tokens'`**
才把额度翻倍（8192 → 16384 → 32768）重发一次，其余解析失败直接抛——
同样的提示词重发一遍还是同样一份坏 JSON。

判据用 `stop_reason` 而不是"语法错误长什么样"：语法错误是截断的**后果**，
拿它当依据会把"模型胡说八道"也当成截断去重发，白花一次调用。
上限 32768 是硬顶，到了就抛，不会无限重发。5 条单测覆盖了这几种分支。

### 15.1 为什么补图会画错

深灰裙子被围裙盖住一大片。切图按深度把这片挖掉、写进 skirt.erased.png 交给
补图填。问题在补图**没有真值**——那片在切图里 alpha 是 0，源图下面到底是
被围裙挡住的裙子还是别的东西，补图看不到，只能照着画面里还看得见的部分推。

围裙正好盖在上面，于是它照着围裙画满了整片：

| 指标 | 值 |
|---|---|
| skirt 擦除区内补图后的像素 | 70014 |
| 平均色差 vs 源图 | R −27.3　G −26.5　B −29.2 |
| 和源图接近（±6）的比例 | **4.3%** |
| skirt ∩ apron 重叠 | 69669px，98% 落在裙子这个擦除区里 |

补出来的是围裙的紫灰 `rgb(108,99,120)`，裙子该有的深灰是 `rgb(69,59,73)`。

**静态切图看不出来**：那片被盖着，预览里不显示。但两片按不同骨头转起来，
围裙那份复制品就跟着裙子的骨头走，露出来就是一层重影——这正是"断裂滑动"
的第二个来源。role7 上另有两个更直观的实例：

```
body<skirt_bottom @(73,604)  源图[108,96,118]  body=[119,113,129]
head<glasses     @(148,118)  源图[225,173,159]  head=[246,183,157]
```

### 15.2 改法：把源图真值贴回去，别让模型编

**先记两条走错的路，免得再回去。**

**错路一：判"源图那块是不是空的"，空的才压 alpha。**

这条门槛是错的，而且是这次的真正教训。源图被盖处**之所以有内容，正是因为
遮挡者本人画在那里**——那不是被盖者自己的真值。拿它当"有没有真值"的判据，
等于要求"被盖的地方源图必须是透明的"，而围裙盖住身体时源图当然不透明。
后果：role7 和 12 的 front **100% 被判成 null**、`.front.png` 压根不落盘，
重影一个没挡住，e2e 反而红在"重复 75.1%"上。

给这条门槛背书的那个例子（眼镜盖脸、脸被压成透明）病根根本不在这里：
MobileSAM 纯框提示，掩码经常**溢出到框外**（实测眼镜掩码 10039px vs 自己
9889px 的内容，多出来的是整张脸）。那是 §15.3 的 `clipToBox` 的事，
不该在这里再用面积比兜一遍。

**错路二：把这片从送模型的掩码里挖掉，落盘保持透明。**

那样会得到一个洞。用户的流程图写得很明确：
「可见区域 **+ 隐藏区域(AI补全/Inpaint)** → **完整 Object RGBA**」——
围裙甩开的时候底下必须有身体，才叫"完整的 Object"。留成透明，
围裙一动就是一片虚空。

**最终做法：有真值就直接贴回去。**

关键认识：源图那个像素**不是猜的**——它就是当时真正显示的颜色。
既然形状要完整（alpha 得给 255）、颜色又有真值，那唯一正确的做法就是把
真值搬过去，模型只该负责源图里彻底空掉的位置。

1. `cutter.js` 写 `.erased.png` 时，顺手把该处**源图原样的 RGB** 写进像素
   （alpha 仍是掩码语义，255 = 被擦；没真值时留 `0,0,0` 当哨兵）。
2. `inpaint.js` 读它，在**选完轮次之后、`bleedAlpha` 之后**，把有真值的
   像素贴回、alpha 给 255。

顺序两个都不能动：贴早了会被 RGB 扩散搅脏；贴早了那大片看不见的像素会
主导质量分，让轮次选择偏向错的一轮。

实测两件素材的擦除区里，真值覆盖率是 **127211 / 127623 = 99.7%**——
也就是说补图真正该发挥的地方只有 **412px**（0.3%）：源图里彻底空掉的那些。

### 15.3 顺带修掉的一个更严重的 bug：小配件把大部件整片擦掉

加 front 的过程里发现，**眼镜把整张脸从 head 上擦掉了**。

MobileSAM 是纯框提示，回来的掩码经常**溢出到框外**。实测眼镜那个框
（67,112 135x111），掩码覆盖 10039px，横跨 x 70..207、y 118..228，
而眼镜自己只有 9889px 的内容——多出来的那片是**整张脸**。
眼镜 depth=3 比 head 的 depth=1 深，于是脸被判给眼镜、从 head 上整片擦掉，
切出来的 head 是一张没有脸的头。

改法：**掩码先夹到部件自己的框里**再进归属表。框是 SAM 的提示，也是这个部件
位置的**上界**——掩码再像，也没道理认领框外的像素。实测这一下裁掉 10224px
外溢掩码。

顺带把遮挡判定收紧：擦除时还要求"归属表判给遮挡者"，不只看掩码。

### 15.4 判据本身也修了一次：什么叫"重复"

**重复量以前只在脚本里，e2e 不测。**`scripts/dup-check.mjs` 是我人工看的，
所以"补图又画了一遍"能一路绿灯过掉整轮 e2e。抽成 `server/api/isolate.js`
的 `checkDuplicates()`，脚本和 e2e 共用同一份口径（两处各写一遍必然漂移）。

但**判据被推翻过两次**，都记在这里。

**① 「同一个源像素被两张切图都画了不透明」—— 错。**

在"完整 Object RGBA"的设计下（§15.2），被盖住那片**本来就应该有内容**：

```
role7：重复 90771/120922px = 75.1%
  12 ：重复 25265/40597px  = 62.2%
```

全是设计使然，正确设计下这个判据永远过不了。当初那两条阈值
（< 25%、擦除区内 < 50%）是按"留洞"那版设的，留洞一去掉就成了墙上的一道假门。
`checkDuplicates` 保留但只打印不判定——重叠率是了解切图结构的窗口。

**② 「补出来的颜色像不像遮挡者」—— 也错，假阳性一片。**

```
handle<tomato  |handle-tomato| = 0 的像素 7260px   ← 看着像重影
```

一查那些点 **handle 和 tomato 都精确等于源图色**，根本不是重影。
那件素材整体偏暗（源图 `rgb(1,0,0)`、`rgb(53,68,2)`），任何两个暗色像素的
绝对色差都低于任何合理门槛。色差只能**相对地**看。

**真正定义重影的是「和真值差多少」。** 源图那一格就是真值——它就是当时真正
显示的颜色（§15.2）。判据 `checkGhosts()`：

```
落在某部件 A 的擦除区、那格有真值、A 在那里不透明，而
dSrc = |A色 - 源图那格色| ≥ 120     （L1，三通道合计 ≈ 每通道 40）
```

实测两个典型：body 在裙摆底下 `[119,113,129]` vs 源图 `[108,96,118]`；
head 在镜片底下 `[246,183,157]` vs 源图 `[225,173,159]`。

两个**必须排除**的（不排除就是纯假阳性）：

- 源图里彻底空掉的真洞（两件素材合计 412px）。补图在那儿编内容是它的
  **职责**，画成什么都不算错。实测 12 的 watermelon_slice 46px"重影"色差
  高达 628，一查全是真洞——补图照着旁边的西瓜画了红瓤和浅绿，完全合理。
- 没真值的擦除区，理由同上。

**阳性对照**（证明判据不是假门）：往干净产物里有真值的擦除区涂一层
"照着自己可见部分画"的色，立刻报 35%。干净产物 0%。

e2e 断言 `ghostOfCovered < 0.05`。实测 role 0.00%、12 0.00%；
这一版之前的中间态 1.9%（全是贴回边缘渗出来的一两像素锯齿，
260 个连通块里 216 个 ≤4px）。

### 15.5 `.erased.png` 一个文件担两件事：alpha 是掩码，RGB 是真值

真值要有地方放，选的是复用 `.erased.png`：**alpha = 掩码**（255 = 被擦），
**RGB = 那格在源图里原样的颜色**（源图那儿本来就空时留 `0,0,0` 当哨兵）。
不加新文件，现有消费方也不用改路径。

代价是**读写都必须认准通道**，而这里翻过两次车，都是静默的：

**写反**（"没被擦的给 alpha=255"）→ 整窗成擦除区，补图把每个部件贴成
100% 不透明的实心矩形：

```
AssertionError: 补图改动了轮廓，这些部件不合格: basket_back
  （不透明 100.0%，已经接近实心矩形）
```

现象指向补图，根因在切图写掩码那一行。第一反应容易去改贴回逻辑，那是错的。

**读错通道**（`data[i*4] > 127` 判掩码，读的是红通道）→ 深色部件的真值像素
（R < 127）被判成"不在擦除区"。实测 role9：

```
[切图] ⌫ shoes 擦除前方遮挡 957px
AssertionError: shoes（957px 悬空不透明：既不连着已有内容、也不在擦除区里）
```

两个数**整整齐齐地相等**就是线索——悬空像素数正好等于擦除数。深色的
鞋子、裙子全中，浅色部件不中。同一处错误散在四个文件里各一份：
`temp/test/e2e.test.js`（`erasedPixels`、`strayOpaque`）、
`server/api/isolate.js`（`checkDuplicates`）、`temp/test/part-isolation.test.js`、
`temp/test/polygon.test.js`。

`baseplate.js` 写的 `_base_plate.erased.png` 是全通道灰度（三通道同 255），
对它读红通道恰好也对——但那是巧合，不是可以依赖的约定。

改这类代码后的自检：**单跑切图、不补图**，数一遍这张掩码的规模。
标注数应 ≈ 日志里那句 `⌫ <部件名> 擦除前方遮挡 Npx`；等于窗口 `w*h` 就是写反了。


## 16. 网格三角剖分自交（2026-09-20 补）

### 16.1 现象与真实规模

`server/api/mesh.js` 的 `triangulate()` 原本是扇形剖分：把「外轮廓一圈 +
内部栅格」所有采样点按质心角度排序，再拿 `order[0]` 连每一对相邻点。
内部栅格点会和边界点落在同一条射线上，扇形于是自己叠上去。

真实部件几何 A/B（role 15 个部件、12.png 6 个部件 × density 4/6/8/12/16/24，
共 12 组）：

| 指标 | 扇形（旧） | 栅格 + 环带缝合（新） |
|---|---|---|
| 重叠三角（重心落在别的三角内） | 50 → 1315 个 | **0** |
| 覆盖偏差 \|面积和 / bbox − 1\| 最大 | 0.22 → 2.83 | **≤ 4e-15** |
| 顶点空间绕向 | 全部顺时针（背朝外） | 全部逆时针 |
| 零面积三角 | 0（已过滤） | 0 |

密度越高越糟：d=24 时 role 的 1380 个三角里 1315 个在互相叠，面积算了将近 4 倍。
危害不是「画不出来」，而是**重叠区域的顶点会被加权变换算两遍**，
接缝处的形变量凭空翻倍。

### 16.2 新剖分

点集结构是已知的，不需要通用三角化算法：

1. 内部 `steps × steps` 栅格按四边形剖分，每格 2 个三角
2. 外轮廓环与栅格外圈之间的环带，按绕中心的展开角归并缝合
   （`stitchRings()`，「谁的下一个点角度小就推进谁」）

两块拼起来正好铺满 bbox。`hull: outer.length` 的语义保持不变——
而且现在剖分本身按下标区分边界点与栅格点，外轮廓排在前面不再只是约定，
排错了会直接串位，所以单测里补了一条 hull 语义断言。

### 16.3 顺手修掉的绕向

`emit()` 里的叉积是在**采样点空间**（Y 向下）算的，而写进 `vertices` 的是
`-p.y`。一次 Y 取负把叉积符号整体翻过来，所以顶点空间的逆时针对应
`area < 0`。旧注释写的是「area < 0 就翻」，实际产出的全是顺时针。
判反了不报错，只是整片网格背朝外，开了背面剔除的运行时会整块不见。

### 16.4 两个验证陷阱

**（一）`Fixed mesh (invalid triangles)` 复现不出来，别拿它当判据。**
这条 Spine 导入警告是最初发现问题的线索，但这次做了 42 次真 Spine CLI 导入
（合成骨架 + role / 12.png 真实几何 × 6 档密度 × unity 4.2 与 cocos-3.8 两个目标），
**新旧两版都是 0 条**。验收只能靠几何度量。

顺带两个导入前提：Spine 编辑器只收单根骨架，而真实分析里 `_base_plate`
和主体各自成根，要导入得先把多余的根挂到第一个根下面；cocos-3.8 目标导出的
骨架同理，直接喂会报 `Skeleton cannot have multiple root bones`。

**（二）量重叠只能从 `mesh.vertices` 取点。**
第一次对比时我从导出的**加权网格** `vertices`（`[n, (bone,x,y,w)*n, ...]`）
按 `Σ bx*w` 反推点集——那是骨骼空间坐标，漏掉骨骼自身的平移，
重建出来的形状已经变形（arm 的「bbox」重建成 15052，真值 12062），
于是报出「新剖分也有 2 个重叠、覆盖只有 0.81」的假结论。
和 14.6 是同一类错误：**判据本身绕了一道会失真的换算**。

回归测试在 `temp/test/skin.test.js`：重叠为 0、面积和 = w×h、全逆时针、hull 语义，
各覆盖 4 种部件形状（含 w≫h 的极扁件）× 7 档密度。
